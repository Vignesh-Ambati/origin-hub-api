================================================================================
  PHASE 1: HELLO WORLD WITH FASTAPI                               [EASY]
================================================================================

  GOAL
    Get a web server running that responds to your browser. Nothing more.
    Resist the urge to add "just one more thing" — the point is the loop:
    edit file -> save -> reload -> see change in browser.

  WHAT YOU WILL LEARN
    - What an HTTP request and response actually are
    - How FastAPI turns a Python function into an HTTP endpoint
    - What --reload does and why it is a dev-only flag

  [ ] 1.1  Create a file: app/__init__.py
           Leave it completely empty. It exists only to tell Python
           "the app folder is a package you can import from."

  [ ] 1.2  Read first (2 minutes): open https://fastapi.tiangolo.com/
           Skim the first example on the homepage. Do not copy it yet.

  [ ] 1.3  Create app/main.py with the smallest possible FastAPI app:
             from fastapi import FastAPI
             app = FastAPI()

             @app.get("/")
             def root():
                 return {"message": "Hello from Origin Hub"}

  [ ] 1.4  VERIFY — start the server:
             .venv\Scripts\activate
             uvicorn app.main:app --reload --port 8000

           EXPECTED: a line like "Uvicorn running on http://127.0.0.1:8000"

  [ ] 1.5  VERIFY — open http://localhost:8000 in your browser.
           EXPECTED: {"message":"Hello from Origin Hub"}

  [ ] 1.6  VERIFY — open http://localhost:8000/docs
           EXPECTED: Swagger UI showing your GET / endpoint.
           Click "Try it out" -> "Execute". See the response inside the docs.

  [ ] 1.7  BREAK IT — with the server running, change the message to
           "Hello v2" and save the file. Watch the terminal.
           EXPECTED: uvicorn prints "Reloading..." and your browser refresh
           shows the new message. THIS is the dev loop. Get used to it.

  [ ] 1.8  BREAK IT AGAIN — stop the server (Ctrl+C). Restart it WITHOUT
           --reload. Change the message. Refresh the browser.
           EXPECTED: message does NOT change. This is why --reload exists
           in dev and is forbidden in production.

  EXPLAIN OUT LOUD BEFORE MOVING ON:
    - What does @app.get("/") actually do to the function below it?
    - What is the URL path in @app.get("/health") if you rename root()?
      (Trick question — the function name does NOT matter. Only the path.)
    - Why did --reload NOT work when you removed it?

  COMMON MISTAKES AT THIS PHASE:
    - Forgetting app/__init__.py -> "ModuleNotFoundError: No module named 'app'"
    - Running uvicorn from the wrong folder -> same error
    - Missing :app in "app.main:app" -> "Error loading ASGI app"


================================================================================
  PHASE 2: CONFIGURATION WITH ENVIRONMENT VARIABLES              [NORMAL]
================================================================================

  GOAL
    Stop hardcoding strings like "Origin Hub" inside Python. Put them in a
    .env file that the app reads at startup. This is how every real app is
    configured — because the value changes between your laptop, staging,
    and production, but the code does not.

  WHAT YOU WILL LEARN
    - What environment variables are
    - How pydantic-settings reads .env and validates values
    - The fail-fast principle: bad config crashes at startup, not at 3 a.m.

  [ ] 2.1  Create app/core/__init__.py (empty file).

  [ ] 2.2  Create app/core/config.py:
             from pydantic_settings import BaseSettings

             class Settings(BaseSettings):
                 PROJECT_NAME: str = "Origin Hub API"
                 ENVIRONMENT: str = "development"
                 API_PREFIX: str = "/api"

                 class Config:
                     env_file = ".env"

             settings = Settings()

  [ ] 2.3  Add to your existing .env.example (and your local .env):
             PROJECT_NAME=Origin Hub API
             ENVIRONMENT=development
             API_PREFIX=/api

  [ ] 2.4  Update app/main.py to use the setting:
             from app.core.config import settings

             @app.get("/")
             def root():
                 return {"message": f"Hello from {settings.PROJECT_NAME}"}

  [ ] 2.5  VERIFY — restart the server (needed because env is read at startup).
           EXPECTED: message now reads "Hello from Origin Hub API".

  [ ] 2.6  BREAK IT — change PROJECT_NAME in .env to "Broken Name".
           Restart the server. Refresh browser.
           EXPECTED: message updates to "Hello from Broken Name".
           Then change it back.

  [ ] 2.7  BREAK IT HARDER — in config.py, change:
             ENVIRONMENT: str = "development"
           to:
             ENVIRONMENT: int = "development"
           Restart the server.
           EXPECTED: a pydantic ValidationError at startup. Read the error
           message carefully. THIS is fail-fast. Fix it back.

  EXPLAIN OUT LOUD BEFORE MOVING ON:
    - Why is reading PROJECT_NAME from .env better than typing it in main.py?
    - Why does changing .env require a server restart but changing main.py
      does not (with --reload)?
    - Where should the real .env file go in Git? (Answer: NOWHERE. Add it to
      .gitignore. Only .env.example is committed.)

  COMMON MISTAKES AT THIS PHASE:
    - Editing .env.example instead of .env -> your app does not see the change
    - Committing .env -> secrets leak into Git history forever
    - Forgetting class Config: env_file = ".env" -> settings ignore .env


================================================================================
  PHASE 3: HEALTH CHECK & ROUTE ORGANIZATION                     [NORMAL]
================================================================================

  GOAL
    Split your routes into files BEFORE you have many of them. Beginners
    put everything in main.py until it becomes 2000 lines and moving it
    becomes a nightmare. Do it now, when there are two routes.

  WHAT YOU WILL LEARN
    - APIRouter: how FastAPI lets you group routes across files
    - URL prefixes: how /api/health is assembled from two pieces
    - The "manifest" pattern: routes/__init__.py importing all routers

  [ ] 3.1  Create app/api/__init__.py (empty).

  [ ] 3.2  Create app/api/routes/__init__.py with:
             from fastapi import APIRouter

             api_router = APIRouter()

  [ ] 3.3  Create app/api/routes/health.py:
             from fastapi import APIRouter

             router = APIRouter()

             @router.get("/health")
             def health_check():
                 return {"status": "healthy", "version": "0.1.0"}

  [ ] 3.4  Update app/api/routes/__init__.py to include the health router:
             from fastapi import APIRouter
             from app.api.routes import health

             api_router = APIRouter()
             api_router.include_router(health.router)

  [ ] 3.5  Update app/main.py to mount api_router:
             from app.api.routes import api_router
             from app.core.config import settings

             app.include_router(api_router, prefix=settings.API_PREFIX)

  [ ] 3.6  VERIFY — http://localhost:8000/api/health
           EXPECTED: {"status":"healthy","version":"0.1.0"}

  [ ] 3.7  VERIFY — http://localhost:8000/health
           EXPECTED: 404 Not Found. The /api prefix is required.

  [ ] 3.8  VERIFY — http://localhost:8000/docs
           EXPECTED: both / and /api/health appear, grouped under "default".

  [ ] 3.9  BREAK IT — change API_PREFIX in .env to "/v1".
           Restart. Try both /api/health and /v1/health.
           EXPECTED: /v1/health works, /api/health is 404.
           Change it back to /api.

  EXPLAIN OUT LOUD BEFORE MOVING ON:
    - In the URL /api/health, which file defines "/api" and which defines "/health"?
    - Why do we import health.py inside routes/__init__.py instead of importing
      it in main.py?
    - If you added a new file routes/users.py, what two lines would you add
      to routes/__init__.py? (Answer: import users; api_router.include_router(users.router).)

  COMMON MISTAKES AT THIS PHASE:
    - Defining the router in health.py as "api_router" instead of "router"
      -> confusing when you have many files
    - Forgetting to include the router in routes/__init__.py -> endpoint never appears
    - Adding the /api prefix twice -> URL becomes /api/api/health


================================================================================
  PHASE 4: CORS — CONNECT YOUR REACT FRONTEND                    [HARD]
================================================================================

  GOAL
    Your React app runs on port 5173. Your API runs on port 8000. To the
    browser, those are different websites, and the browser will block the
    React app from calling the API unless you explicitly allow it.

  WHAT YOU WILL LEARN
    - What "origin" means (scheme + host + port)
    - Why the browser enforces CORS even when your backend does not care
    - The rule that will save you from a security incident later:
      NEVER allow_origins=["*"] together with allow_credentials=True

  [ ] 4.1  Add to app/core/config.py:
             FRONTEND_URL: str = "http://localhost:5173"

  [ ] 4.2  Add to .env.example (and your .env):
             FRONTEND_URL=http://localhost:5173

  [ ] 4.3  Update app/main.py to add CORSMiddleware:
             from fastapi.middleware.cors import CORSMiddleware

             app.add_middleware(
                 CORSMiddleware,
                 allow_origins=[settings.FRONTEND_URL],
                 allow_credentials=True,
                 allow_methods=["*"],
                 allow_headers=["*"],
             )

  [ ] 4.4  VERIFY — in your React app, add a quick fetch:
             fetch("http://localhost:8000/api/health", { credentials: "include" })
               .then(r => r.json())
               .then(console.log)

           EXPECTED: the health JSON object in the browser console,
           with NO red CORS error.

  [ ] 4.5  BREAK IT — temporarily change allow_origins to
           ["http://localhost:9999"] (wrong port). Reload the React page.
           EXPECTED: browser console shows a CORS error. Read it. This is
           the error you will see a hundred more times. Get familiar with it.
           Then fix it back.

  [ ] 4.6  BREAK IT DANGEROUSLY — change allow_origins=["*"] AND leave
           allow_credentials=True. Reload.
           EXPECTED: FastAPI will refuse or the browser will refuse. This
           combination is banned for a reason. Understand why before you
           move on: a wildcard origin means ANY website can send
           authenticated requests as your logged-in user.

  EXPLAIN OUT LOUD BEFORE MOVING ON:
    - Why is http://localhost:5173 a different "origin" from
      http://localhost:8000 even though both are on your laptop?
    - What does credentials: "include" tell the browser to do?
    - Why must allow_origins list exact URLs when cookies are in play?

  COMMON MISTAKES AT THIS PHASE:
    - Using "*" with credentials -> silent failure or security hole
    - Forgetting the http:// in the origin -> never matches
    - Adding a trailing slash to the origin -> never matches
    - CORS errors are a browser thing, not a server thing — curl will
      still work even when the browser blocks you. This confuses beginners
      constantly. Do not trust curl to diagnose a CORS problem.


================================================================================
  PHASE 5: YOUR FIRST TEST                                       [NORMAL]
================================================================================

  GOAL
    Stop verifying everything by clicking in the browser. Write one test
    that checks /api/health returns 200. This is the habit that separates
    people who ship from people who debug.

  WHAT YOU WILL LEARN
    - What a test actually is (input -> call -> assertion)
    - How FastAPI's TestClient runs the app without a real server
    - How pytest discovers files

  [ ] 5.1  Create tests/__init__.py (empty).

  [ ] 5.2  Create tests/test_health.py:
             from fastapi.testclient import TestClient
             from app.main import app

             client = TestClient(app)

             def test_health_returns_200():
                 response = client.get("/api/health")
                 assert response.status_code == 200

             def test_health_returns_healthy_status():
                 response = client.get("/api/health")
                 assert response.json()["status"] == "healthy"

  [ ] 5.3  Run: pytest
           EXPECTED: "2 passed" in green.

  [ ] 5.4  Run: pytest -v
           EXPECTED: each test printed by name with PASSED. Get used to -v.

  [ ] 5.5  BREAK IT — change one assertion to == 999. Run pytest.
           EXPECTED: a red failure with the actual value shown. Read the
           output. This is what a failing test looks like. Fix it back.

  [ ] 5.6  BREAK IT HARDER — delete the /api/health route from health.py.
           Run pytest.
           EXPECTED: the test now fails with 404. This is exactly what tests
           are for: they caught that you broke a route. Undo the deletion.

  EXPLAIN OUT LOUD BEFORE MOVING ON:
    - Why is test_health.py discovered by pytest but health.py is not?
    - What is the difference between TestClient(app) and running uvicorn?
    - Why do we test both status_code AND json()["status"]?
      (Answer: 200 with the wrong body is still a bug.)

  COMMON MISTAKES AT THIS PHASE:
    - Naming the file test-health.py (dash) -> pytest ignores it
    - Naming the file health_test.py -> pytest ignores it (must be test_*)
    - Forgetting pythonpath=["."] in pyproject.toml -> "No module named 'app'"


================================================================================
  PHASE 6: DATABASE — POSTGRESQL + SQLALCHEMY                    [HARD]
================================================================================

  GOAL
    Connect the app to a real PostgreSQL database. At the end of this phase
    you will be able to run SELECT 1 through SQLAlchemy from a Python REPL.
    No models, no tables yet — just the connection.

  WHAT YOU WILL LEARN
    - What a database engine and a session are
    - Why sessions must be closed (get_db yields, not returns)
    - Why config values must live in .env, not in code

  [ ] 6.1  Install PostgreSQL if you haven't. On Windows, the official
           installer from postgresql.org is fine. Remember the password
           you set for the "postgres" user.

  [ ] 6.2  Using pgAdmin or psql, create a database:
             CREATE DATABASE origin_hub;

  [ ] 6.3  Add to pyproject.toml dependencies:
             "sqlalchemy>=2.0.0,<3.0.0",
             "psycopg[binary]>=3.1.0,<4.0.0",
             "alembic>=1.15.0,<2.0.0",

           NOTE: use psycopg (v3), not psycopg2. The old tutorial you find
           online probably uses psycopg2 — that is deprecated.

  [ ] 6.4  Run: pip install -e ".[test]"

  [ ] 6.5  Add to app/core/config.py:
             DATABASE_URL: str

           NOTE: no default. This forces the value to exist in .env, which
           is what you want. Missing DB config should crash at startup.

  [ ] 6.6  Add to .env and .env.example:
             DATABASE_URL=postgresql+psycopg://postgres:YOUR_PASSWORD@localhost:5432/origin_hub

           The "+psycopg" part tells SQLAlchemy which driver to use.

  [ ] 6.7  Create app/db/__init__.py (empty).

  [ ] 6.8  Create app/db/base.py:
             from sqlalchemy.orm import DeclarativeBase

             class Base(DeclarativeBase):
                 pass

  [ ] 6.9  Create app/db/session.py:
             from sqlalchemy import create_engine
             from sqlalchemy.orm import sessionmaker
             from app.core.config import settings

             engine = create_engine(settings.DATABASE_URL, echo=True)
             SessionLocal = sessionmaker(bind=engine, autoflush=False, autocommit=False)

             def get_db():
                 db = SessionLocal()
                 try:
                     yield db
                 finally:
                     db.close()

  [ ] 6.10 VERIFY — from a Python REPL:
             .venv\Scripts\activate
             python
             >>> from app.db.session import engine
             >>> from sqlalchemy import text
             >>> with engine.connect() as conn:
             ...     print(conn.execute(text("SELECT 1")).scalar())
             1

           EXPECTED: prints 1. If it does not, your DATABASE_URL is wrong.
           Read the error. It will tell you exactly which part is wrong.

  [ ] 6.11 BREAK IT — change the password in DATABASE_URL to "wrong".
           Run the same REPL snippet.
           EXPECTED: an authentication error. Read it. You will see this
           error many times when deploying. Get familiar.
           Fix the password back.

  EXPLAIN OUT LOUD BEFORE MOVING ON:
    - What is the difference between engine and SessionLocal?
    - Why does get_db() use yield instead of return?
    - What happens if a request raises an exception after get_db() yields
      but before the response? (Answer: the finally block still runs and
      closes the session. That is the point.)

  COMMON MISTAKES AT THIS PHASE:
    - Forgetting +psycopg in the URL -> SQLAlchemy cannot find the driver
    - Using "postgresql://" without a driver spec -> same error
    - echo=True left on in production -> log spam. Fine for learning.
    - Special characters in the DB password (like @ or :) -> URL parsing
      breaks. URL-encode them or pick a simpler password for local dev.


================================================================================
  PHASE 7: USER MODEL & DATABASE MIGRATION                       [HARD]
================================================================================

  GOAL
    Define what a "user" looks like in your database and let Alembic create
    the table. At the end you will open pgAdmin and literally see a users
    table with the columns you declared.

  WHAT YOU WILL LEARN
    - ORM models: Python classes that map to SQL tables
    - Alembic: version-controlled schema changes
    - Why you never write CREATE TABLE by hand in a real project

  [ ] 7.1  Create app/models/__init__.py (empty).

  [ ] 7.2  Create app/models/user.py:
             from datetime import datetime
             from sqlalchemy import String, Boolean, DateTime, func
             from sqlalchemy.orm import Mapped, mapped_column
             from app.db.base import Base

             class User(Base):
                 __tablename__ = "users"

                 id: Mapped[int] = mapped_column(primary_key=True)
                 email: Mapped[str] = mapped_column(String(255), unique=True, index=True)
                 hashed_password: Mapped[str | None] = mapped_column(String(255), nullable=True)
                 is_active: Mapped[bool] = mapped_column(Boolean, default=True)
                 created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())

  [ ] 7.3  IMPORTANT: update app/db/base.py so Alembic can see the model.
           Alembic only detects models that have been imported.
           Add at the bottom:
             from app.models.user import User  # noqa: F401

           Without this line, the next step generates an EMPTY migration.
           This is the #1 beginner Alembic mistake.

  [ ] 7.4  Initialize Alembic: alembic init alembic
           This creates an alembic/ folder and alembic.ini.

  [ ] 7.5  Edit alembic/env.py:
           - Import: from app.core.config import settings
           - Import: from app.db.base import Base
           - Replace: target_metadata = None
             With:    target_metadata = Base.metadata
           - Find where it sets sqlalchemy.url and set it from settings:
             config.set_main_option("sqlalchemy.url", settings.DATABASE_URL)

  [ ] 7.6  Generate the migration:
             alembic revision --autogenerate -m "create users table"

           EXPECTED: a new file in alembic/versions/. OPEN IT. Read it.
           It should contain op.create_table('users', ...). If it is empty,
           you forgot step 7.3.

  [ ] 7.7  Apply the migration: alembic upgrade head

  [ ] 7.8  VERIFY — in pgAdmin, refresh the origin_hub database, expand
           Schemas -> public -> Tables. You should see: users, and
           alembic_version.

  [ ] 7.9  VERIFY — via psql or pgAdmin query tool:
             SELECT column_name, data_type FROM information_schema.columns
             WHERE table_name = 'users';
           EXPECTED: rows for id, email, hashed_password, is_active, created_at.

  [ ] 7.10 BREAK IT — add a new column to the User model (e.g. username).
           Run:
             alembic revision --autogenerate -m "add username"
             alembic upgrade head
           Open pgAdmin. The column exists.
           Now DOWNGRADE: alembic downgrade -1
           Refresh pgAdmin. The column is gone.
           This is the point of migrations: schema changes are reversible,
           versioned, and reproducible.

  EXPLAIN OUT LOUD BEFORE MOVING ON:
    - Why is hashed_password nullable=True? (Hint: Google login has no password.)
    - What is the difference between alembic revision and alembic upgrade?
    - Why is server_default=func.now() better than default=datetime.utcnow?
      (Answer: the database sets the time, not the app. Clock skew between
      app servers becomes irrelevant.)

  COMMON MISTAKES AT THIS PHASE:
    - Forgetting to import the model in base.py -> empty migration
    - Editing the autogenerated migration by hand without understanding it
    - Running alembic upgrade without running revision first -> nothing to apply
    - Forgetting to run upgrade after generating a revision -> table missing


================================================================================
  PHASE 8: PASSWORD HASHING                                      [NORMAL]
================================================================================

  GOAL
    Two functions: hash a password, verify a password against a hash.
    You will never store or log a plain password again.

  WHAT YOU WILL LEARN
    - Why hashing is one-way and encryption is not
    - What Argon2id is and why OWASP recommends it over bcrypt in 2024+
    - The concept of a "salt" (handled for you by the library)

  [ ] 8.1  Add to pyproject.toml: "argon2-cffi>=23.1.0,<25.0.0"
           Run: pip install -e ".[test]"

  [ ] 8.2  Create app/core/security.py:
             from argon2 import PasswordHasher
             from argon2.exceptions import VerifyMismatchError

             _hasher = PasswordHasher()

             def hash_password(plain: str) -> str:
                 return _hasher.hash(plain)

             def verify_password(plain: str, hashed: str) -> bool:
                 try:
                     _hasher.verify(hashed, plain)
                     return True
                 except VerifyMismatchError:
                     return False

  [ ] 8.3  VERIFY — in a Python REPL:
             from app.core.security import hash_password, verify_password
             h = hash_password("test123")
             print(h)                       # starts with $argon2id$
             print(verify_password("test123", h))   # True
             print(verify_password("wrong",   h))   # False

  [ ] 8.4  VERIFY — run hash_password("test123") TWICE. The two outputs
           are DIFFERENT. This is the salt at work. Both still verify
           correctly. This is why you cannot compare hashes with ==.

  [ ] 8.5  BREAK IT — try verify_password("test123", "not-a-hash").
           EXPECTED: the library raises InvalidHashError, NOT VerifyMismatch.
           Your current function will crash. Read the error.
           Fix it: catch argon2.exceptions.InvalidHashError too and return False.
           This is why you read the docs, not just the tutorial.

  EXPLAIN OUT LOUD BEFORE MOVING ON:
    - Why can't you "decrypt" a hash to get the password back?
    - Why is Argon2id preferred over MD5 or SHA-256 for passwords?
    - What is the salt and what attack does it prevent?
      (Answer: rainbow tables. Two users with the same password get
      different hashes.)

  COMMON MISTAKES AT THIS PHASE:
    - Using hashlib.sha256 instead of argon2 -> fast hash = easy to brute-force
    - Storing the plain password "temporarily for debugging" -> breach waiting to happen
    - Comparing hashes with == -> always False because of the salt


================================================================================
  PHASE 9: PYDANTIC SCHEMAS                                      [NORMAL]
================================================================================

  GOAL
    Define the shape of data coming INTO your API and going OUT. Pydantic
    validates inputs automatically and rejects garbage before your code runs.

  WHAT YOU WILL LEARN
    - The difference between a "schema" (API contract) and a "model" (DB table)
    - How FastAPI uses schemas to auto-generate the Swagger docs
    - Why UserResponse must NEVER include hashed_password

  [ ] 9.1  Add to pyproject.toml: "email-validator>=2.0.0"
           (Required for EmailStr.) Run pip install.

  [ ] 9.2  Create app/schemas/__init__.py (empty).

  [ ] 9.3  Create app/schemas/auth.py:
             from datetime import datetime
             from pydantic import BaseModel, EmailStr, Field

             class UserRegisterRequest(BaseModel):
                 email: EmailStr
                 password: str = Field(min_length=8, max_length=128)

             class UserLoginRequest(BaseModel):
                 email: EmailStr
                 password: str

             class UserResponse(BaseModel):
                 id: int
                 email: EmailStr
                 is_active: bool
                 created_at: datetime

                 model_config = {"from_attributes": True}

  [ ] 9.4  VERIFY — in a REPL:
             from app.schemas.auth import UserRegisterRequest
             UserRegisterRequest(email="not-an-email", password="short")
           EXPECTED: pydantic ValidationError listing BOTH problems
           (invalid email AND password too short) in one shot.

  [ ] 9.5  BREAK IT — remove model_config from UserResponse.
           Later, when you return a User ORM object from an endpoint, it
           will fail. Remember this when you get there. For now, just
           understand: from_attributes=True tells Pydantic "you can read
           this data from an object's attributes, not just a dict".

  EXPLAIN OUT LOUD BEFORE MOVING ON:
    - Why do we have both a User model AND a UserResponse schema?
      (Answer: the model has hashed_password; the response must not.)
    - What does EmailStr do that str does not?

             import secrets
             from datetime import datetime, timedelta, timezone
             from sqlalchemy.orm import Session as OrmSession
             from app.models.session import Session

             SESSION_LIFETIME = timedelta(days=7)

             def create_session(db: OrmSession, user_id: int,
                                user_agent: str | None = None,
                                ip_address: str | None = None) -> str:
                 token = secrets.token_urlsafe(32)
                 session = Session(
                     session_token=token,
                     user_id=user_id,
                     expires_at=datetime.now(timezone.utc) + SESSION_LIFETIME,
                     user_agent=user_agent,
                     ip_address=ip_address,
                 )
                 db.add(session)
                 db.commit()
                 return token

             def get_valid_session(db: OrmSession, token: str) -> Session | None:
                 session = db.query(Session).filter(Session.session_token == token).first()
                 if session is None:
                     return None
                 if session.expires_at < datetime.now(timezone.utc):
                     return None
                 return session

             def delete_session(db: OrmSession, token: str) -> None:
                 db.query(Session).filter(Session.session_token == token).delete()
                 db.commit()

  [ ] 12.1 Add to app/api/routes/auth.py:
             from fastapi import Response
             from app.schemas.auth import UserLoginRequest
             from app.core.security import verify_password
             from app.core.config import settings
             from app.services.session_service import create_session

             @router.post("/login", response_model=UserResponse)
             def login(payload: UserLoginRequest, response: Response,
                       db: OrmSession = Depends(get_db)):
                 user = db.query(User).filter(User.email == payload.email).first()
                 if not user or not user.hashed_password:
                     raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED,
                                         detail="Invalid credentials")
                 if not verify_password(payload.password, user.hashed_password):
                     raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED,
                                         detail="Invalid credentials")
                 token = create_session(db, user.id)
                 response.set_cookie(
                     key=settings.SESSION_COOKIE_NAME,
                     value=token,
                     httponly=settings.COOKIE_HTTPONLY,
                     secure=settings.COOKIE_SECURE,
                     samesite=settings.COOKIE_SAMESITE,
                     max_age=7 * 24 * 3600,
                 )
                 return user

             from fastapi import Depends, HTTPException, Request, status
             from sqlalchemy.orm import Session as OrmSession
             from app.db.session import get_db
             from app.core.config import settings
             from app.models.user import User
             from app.services.session_service import get_valid_session

             def get_current_user(request: Request,
                                  db: OrmSession = Depends(get_db)) -> User:
                 token = request.cookies.get(settings.SESSION_COOKIE_NAME)
                 if not token:
                     raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED,
                                         detail="Not authenticated")
                 session = get_valid_session(db, token)
                 if session is None:

                                         detail="Session expired or invalid")
                 user = db.query(User).filter(User.id == session.user_id).first()
                 if user is None or not user.is_active:
                     raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED,
                                         detail="Not authenticated")
                 return user
